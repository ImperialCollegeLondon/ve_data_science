    Running Virtual Ecosystem on the HPC

    Author: moi-taiga

    Introduction to submitting Virtual Ecosystem runs as a PBS array job on the HPC cluster. The workflow was developed for the CX3 cluster, which uses the PBS job scheduler. CX3 is scheduled to be shut down in May 2027.

    Before you start

    You need:

    • a terminal;
    • access to CX3

    Connect to the HPC using SSH

    Use SSH to access the cx3 cluster; you will be required to use your password for authentication.

    ssh userid@login.cx3.hpc.imperial.ac.uk

    See the Imperial RCS documentation for further information about connecting to the cluster. If you are new to HPC environments, do make sure that you familiarise yourself with the documentation. It is highly recommended to attend the Introduction to HPC at Imperial course , but if you cannot make it, the materials for the course are freely available and give a good overview of how to work with the system.

    Importantly: Login nodes are intended for tasks such as editing files, preparing jobs, and submitting jobs. Computationally intensive work should be submitted to compute nodes through PBS.

    Clone the repository

    The project datafiles are shared via GLOBUS from the path:

    /rds/general/project/virtual_rainforest/live/ve_data_science/

    This directory is also the root for a clone of the ve_data_science repository but it is really important that this clone is kept up to date and on the main branch. This ensures that the code files available through GLOBUS are synchronized with the data files they run.

    For this reason, you must use a personal checkout of the ve_data_science repository into your own user directory to run code. This is like using the local clone on your own computer: it isolates the code you are running from other users and also avoids altering the code files served through GLOBUS.

    cd ~
git clone https://github.com/ImperialCollegeLondon/ve_data_science.git
cd ve_data_science

    Traceability and code versions

    When you run code on the HPC, you need to be able to trace the outputs back to the versions of any ve_data_science code being used and the version of Virtual Ecosystem being run. The Virtual Ecosystem will include version information in the output log but you need to ensure that you are using specific named releases and then documenting which releases were used.

    For the ve_data_science code this means taking care to check which branch is currently checked out: you are likely to be using the current code in main.

    Install uv and create a virtual environment

    See uv setup for instructions about using uv. Note that by default uv is configured to use the most recent release on PyPi, but you can specify to run using the most recent code by setting --group dev to alter the uv dependency group with the uv sync and uv run commands below.

    uv venv
uv sync

    Install the example data/configs

    For testing the HPC workflow, install the example data and configuration files:

    uv run ve_run --install-example .

    Create a array job configuration

    Create a TOML job specification that describes the Virtual Ecosystem runs in the array. You can produce the job entries with a sampling method such as Morris, Sobol, or Latin hypercube sampling. A small example is available in hpc_jobs/example_hpc_configs/arrayJob_config.toml.

    The specification has four parts:

    • site_directory: the absolute path to the directory containing the shared configuration files and input data. Replace the path in the example with the path to your checkout's ve_example directory.
    • common_config_paths: paths to configuration files, relative to site_directory, that every array sub-job uses.
    • [[subJobs]]: one or more job entries. Each can provide additional config_paths and a cli_config table of values that override the loaded configuration.
    • repeats: a positive integer on each job entry. The total number of PBS array sub-jobs is the sum of all repeats values.

    Submit the PBS array job

    The submission script takes three arguments:

    1. the array job configuration TOML file;
    2. the PBS resources configuration TOML file (see Choose job resources);
    3. a new output directory for the completed array run.

    The output directory must not already exist. The script creates it and then creates one child directory per PBS array sub-job. From the repository root, run:

    uv run python -m hpc_jobs.submit_ve_array_job \
    hpc_jobs/example_hpc_configs/arrayJob_config.toml \
    hpc_jobs/example_hpc_configs/pbs_resources_config.toml \
    ve_example/<experiment-output>

    The submission script loads and validates both TOML configuration files using Pydantic. By default, it also validates each Virtual Ecosystem configuration before creating the requested output directory, and submitting the array using qsub. It creates an array_subJob_<index> directory for each sub-job. Validation happens before the output directory is created or any jobs are submitted, so invalid configurations fail fast.

    For known-good Virtual Ecosystem configurations, add --skip-ve-validation to skip their model-level validation:

    uv run python -m hpc_jobs.submit_ve_array_job \
    hpc_jobs/example_hpc_configs/arrayJob_config.toml \
    hpc_jobs/example_hpc_configs/pbs_resources_config.toml \
    ve_example/<experiment-output> \
    --skip-ve-validation

    This option does not skip loading, TOML parsing, or Pydantic validation of the array job and PBS resources configuration files.

    Monitor jobs

    Use PBS commands to inspect or cancel jobs:

    List your active jobs:

    qstat -u "$USER"

    Inspect a completed job:

    qstat -x -f <job_id>

    Cancel a job:

    qdel <job_id>

    Each array sub-job receives an array_subJob_<index> directory. The combined PBS standard output and standard error are written to pbs.log; the Virtual Ecosystem log is written to ve.log, and model outputs are written in the same directory:

    ve_example/<experiment-output>/
    array_subJob_1/
        pbs.log
        ve.log
        compiled_configuration.toml
        model_data.nc

    hpc_jobs/run_subJob.py does not write these files directly to the sub-job's output directory. Virtual Ecosystem writes its outputs (including the intermediate Zarr store) to a staging directory under the compute node's local $TMPDIR. Once the run completes, the Zarr store is deleted, and the remaining files (the NetCDF conversion, compiled configuration, and logs) are moved into the sub-job's array_subJob_<index> directory. This keeps the large number of small files generated by the Zarr store off shared/quota-limited storage entirely.

    Choose job resources

    The PBS resource request is defined in a resource configuration TOML file. hpc_jobs/example_hpc_configs/pbs_resources_config.toml has a small allocation suitable for the example data.

    Every value applies to each individual array sub-job, apart from max_concurrent_jobs, which caps how many sub-jobs the scheduler runs at once.

    Larger datasets may require more memory, CPUs, or wall time. More jobs don't need more resources as resources are set per job.

    hpc_jobs/parse_resources_config.py loads and validates the resource configuration, while hpc_jobs/parse_arrayJob_config.py loads and validates the array job configuration. Each resource field is bounds checked, and an out-of-range value aborts the submission with an error rather than sending a bad request to qsub:

    Field Allowed range
    ncpus 1–128
    mem_gb 1–4000
    walltime_hours 0–59
    walltime_minutes 0–59
    max_concurrent_jobs 1–100

    The upper bounds match the largest CX3 nodes rather than realistic per-job requests, so staying inside them does not guarantee that a job will be scheduled promptly. Check the Imperial RCS documentation for more detail.

    Manage file quotas

    Each array sub-job now produces a small, fixed set of output files (pbs.log, ve.log, compiled_configuration.toml, model_data.nc, and any per-model CSV outputs) because the Zarr store, which previously generated approximately 3,600 files per sub-job, is written to the compute node $TMPDIR space and deleted once the NetCDF conversion completes. It is never copied to shared storage. This reduces the file-count pressure on HPC storage quotas for large array runs.

    Check your current usage with:

    quota
